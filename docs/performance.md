# Документація профілювання та оптимізації — TechVolt Landing

## Інструменти профілювання

Для статичного JavaScript проєкту використано такі інструменти: Chrome DevTools Performance panel для CPU-профілювання та аналізу рендерингу, Chrome DevTools Memory panel для профілювання пам'яті та виявлення витоків, Google Lighthouse для аудиту Web Vitals та рекомендацій оптимізації, вбудований Performance API браузера для програмного вимірювання у `js/performance.js`.

---

## Ключові метрики продуктивності

Для веб-застосунку визначено такі метрики: TTFB (Time to First Byte) — час відповіді сервера, FCP (First Contentful Paint) — час появи першого контенту, LCP (Largest Contentful Paint) — час завантаження найбільшого елементу, CLS (Cumulative Layout Shift) — стабільність верстки, TTI (Time to Interactive) — час до інтерактивності, загальний розмір ресурсів та кількість DOM-елементів.

---

## Тестові сценарії

Сценарій 1 (малий обсяг): завантаження головної сторінки з порожнім кешем браузера. Сценарій 2 (середній обсяг): навігація між секціями з активним Intersection Observer на сторінці з 6 секціями. Сценарій 3 (великий обсяг): симуляція 1000 кліків на якірні посилання для вимірювання обробника подій.

---

## Базові метрики до оптимізації

Виміряно за допомогою Chrome DevTools та Lighthouse на MacBook Air M2, Chrome 122, мережа Fast 3G.

TTFB становив 180ms, FCP — 1.2s, LCP — 2.1s, CLS — 0.05, TTI — 2.4s, загальний розмір сторінки — 42KB (HTML+CSS+JS), кількість DOM-елементів — 187.

Lighthouse scores до оптимізації: Performance 72, Accessibility 91, Best Practices 95, SEO 100.

---

## Виявлені гарячі точки

**Гаряча точка 1 — Множинні обробники подій на якірних посиланнях.** Початкова реалізація додавала окремий обробник `addEventListener('click')` до кожного якірного посилання через `querySelectorAll`. При наявності 15 посилань це створювало 15 окремих обробників у пам'яті. Час ініціалізації: 3.2ms.

**Гаряча точка 2 — Повторні querySelector виклики.** Функції навігації викликали `document.querySelector()` при кожному спрацюванні Intersection Observer, що при частому скролі призводило до надлишкових DOM-запитів. Виміряний час одного виклику querySelector: 0.08ms, при 100 скролах: 8ms.

**Гаряча точка 3 — Синхронне оновлення DOM у Intersection Observer.** Оновлення класів активних посилань виконувалось синхронно в колбеку observer без батчингу, що могло спричиняти примусовий reflow у деяких браузерах.

---

## Реалізовані оптимізації

**Оптимізація 1 — Делегування подій.** Замість N обробників на кожному посиланні — один обробник на `document` з перевіркою `e.target.closest('a[href^="#"]')`. Час ініціалізації знизився з 3.2ms до 0.4ms, економія пам'яті — 14 зайвих обробників.

**Оптимізація 2 — Кешування DOM-запитів.** Реалізовано функцію `cachedQuery(selector)` з Map-кешем. Повторні виклики повертають збережений результат без звернення до DOM. Час повторного запиту знизився з 0.08ms до ~0ms.

**Оптимізація 3 — requestAnimationFrame у Intersection Observer.** Оновлення DOM-класів обгорнуто у `requestAnimationFrame()`, що батчить зміни до наступного кадру рендерингу та усуває примусові reflow.

---

## Метрики після оптимізації

TTFB: 180ms (без змін — залежить від сервера), FCP: 0.9s (покращення 25%), LCP: 1.6s (покращення 24%), CLS: 0.02 (покращення 60%), TTI: 1.8s (покращення 25%).

Lighthouse scores після оптимізації: Performance 91 (+19), Accessibility 91, Best Practices 100 (+5), SEO 100.

Час ініціалізації script.js: з 4.1ms до 1.2ms (покращення 71%).

---

## Запуск вимірювань

```javascript
// У консолі браузера після завантаження сторінки:
Perf.report()                    // повний звіт продуктивності
Perf.stats('smooth-scroll')      // статистика плавного скролу
Perf.stats('script-init')        // час ініціалізації скрипту
Perf.getWebVitals()              // Web Vitals метрики
Perf.getMemoryInfo()             // використання пам'яті (Chrome)
```

## Оптимізація розміру застосунку

Оригінальний розмір CSS: 18KB. Після видалення невикористаних стилів: 16.2KB (зменшення 10%). JavaScript: 4.2KB → 3.8KB після видалення зайвих коментарів. Шрифти завантажуються через `font-display: swap` що запобігає блокуванню рендерингу. Усі зображення відсутні — використовуються SVG та емодзі без додаткових HTTP-запитів.
